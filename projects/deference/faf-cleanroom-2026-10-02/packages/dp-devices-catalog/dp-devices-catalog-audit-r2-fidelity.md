## 3. Non-blocking issues

**N1 — `tys_strict_dilemma` (`Remark314.lean`): docstring `Kind: P`, ledger `N+`.** Round 1 (fidelity N8 / adversarial 4b) asked for `N+` since `Dilemma` is an existential and the theorem exhibits a witness; the repair relabelled the ledger row ("N+ (an exhibited witness)") but not the docstring, which still reads `Kind: P`. One-word fix in the docstring. (Every other headline's docstring Kind matches its ledger Kind; checked by script and by eye.)

**N2 — `Dilemma` carries no "selection" half (design note on the `D` proposal; probe P1–P4).** `Dilemma κ obs AP 𝒞 v := ∃ I ∈ AP, ∃ C ∈ 𝒞 I, IsCalibrated κ … ∧ v ≤ value C I.B` is exactly ¬`FailsRegardlessOfLabel` with a witness, as its docstring says ("rendered as the direct negation-with-a-witness"). SL-17's "dilemma of selection (Remark 5.2)" is a *multiplicity*: a calibrated label at which the family fails (`π = 0`, value `5`) **and** a calibrated label at which a member attains `10`. `Dilemma` asks only for the second. Probe: the class of **all** procedures (`fun _ => Set.univ`), which fails at no label, is a `Dilemma` on `Σ_{B_P}` at strict (P1, via `tysStateOne`), limit (P2, via `tysState`) and masked (P3, via `tysStateWayOut`). So `tys_strict_dilemma` proves "the zero-respecting class does not fail regardless of label at the strict sense" and nothing about selection. The failing half *is* proved, outside `Dilemma`: at the stipulated label every zero-respecting member has `V = 5 < 10` (`tys_value_of_zeroRespecting`) and `C₀` is strictly calibrated there (`tys_fiveTen_strictOC`); probe P4 states the conjunction. The verdict theorems' plain-words ledger claim ("strict: a dilemma (the `π = 1` label lets `C*` in)") matches what is proved, so this is not a misstatement; but a reader of the name `tys_strict_dilemma` will expect Remark 5.2's two-label multiplicity. Fix I would accept: either add the conjunct `∃ I ∈ AP, IsCalibrated-for-some-member ∧ ∀ C ∈ 𝒞 I, IsCalibrated κ … → value C I.B < v` to `Dilemma` (and discharge it with `tysState`), or ship `tys_strict_selection : (∀ C, ZeroRespecting tysState tysActEv C → value C toldYouSo < 10) ∧ StrictOC tysState tysObs procFiveTen toldYouSo ∧ Dilemma .strict …` and point the ledger row at it; at minimum say in `Dilemma`'s docstring that the failing-label half is not part of the definition.

**N3 — `tnV2_pureOpt_iff` docstring claims a clause the statement lacks.** The docstring says "`(1,1)` is the unique maximiser among the four pure policies iff `(2p−1)L > S` (and a maximiser iff `≥`)". The statement is the strict iff only; the "`≥`" half is not stated. It is true (`V(1,1) − V(1,2) = (2p−1)L − pS`, `V(1,1) − V(2,1) = (2p−1)L − (1−p)S`, `V(1,1) − V(2,2) = (2p−1)L − S`, and `S ≥ pS, (1−p)S` for `p ∈ [0,1]`, `S > 0`; not machine-checked) but either prove it or drop the parenthetical.

**N4 — F9's repair did not reach the Lean docstrings or the ledger.** Round 1 N6 asked that "ill-posed until `k` is fixed" become "underspecified in `k`, confirmed at `k = 10`"; the findings file now says so, but `LabelReading.lean`'s module docstring (line 24: "ill-posed until `k` is fixed"), `probe_threshold`'s docstring ("without a fixed `k` it is ill-posed") and the ledger's `probeTree` row Status ("dp-sl-065's decimal ill-posed until `k` is fixed (F9)") still carry the old wording. **N5 — T8 "Dev rows" ledger row: "not `(1,2)`" is proved for the mixed sense only.** The row covers `CoherentPureAt` and `CoherentAt` together and says TN-V2 "`(1,1)`, `(2,2)`, not `(1,2)`". `tnV2_coherent_cells` proves `¬ Coherent (1,2)` (mixed); `¬ CoherentPure (1,2)` is not stated (pure coherence is weaker, so it does not follow). **N6 — `GridVerdict`'s Fidelity line says `exact` with a refinement in parentheses.** ZO-19's rule as printed ("`T*` means no violation with some queried point vacuous; `vac` means every queried point vacuous") does not by itself make `T*` and `vac` disjoint; the package adds "some substantive point" to `T*`.
