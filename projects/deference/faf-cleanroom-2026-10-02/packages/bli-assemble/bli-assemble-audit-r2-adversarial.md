## 3. Non-blocking issues

N1 — **The handoff miscounts the cost of `sentencesUpTo`: it is doubly exponential in `K`, hence exponential (not polynomial) in `|S n|`.** `bli-assemble-handoff` stage 5 says `smallList` is "the mathematical version (`sentencesUpTo`, exponential in `K` as a list, which is polynomial in `|S n|`)". From the definition, `|sentencesUpTo (K+1)| = 4^(K+1) + 1 + 3 · |sentencesUpTo K|²` as a list (every pair of the previous level under each of three connectives), so the length squares at each level: `5, 92, 25457, ≈ 1.9·10⁹, ≈ 1.1·10¹⁹, …` (the first three printed by `SmallListEval.lean`), i.e. `≥ c^(2^K)`. Meanwhile `|S n|` with `K = sizeBound n` is singly exponential: a sentence of token size `≤ K` is determined by its digit stream, a string of length `≤ K` over five symbols, so `|S n| ≤ 5^(K+1)` (and `≥ 4^(K-1) − 5` from the atoms alone). So `smallList n` takes exponentially many steps in `|S n|`. Consequences: (i) nothing for target 5 — `Computable` has no cost, and `smallList_toFinset` is what it needs; (ii) for target 6 (iii) the sentence should be deleted: `sentencesUpTo` is not the mathematical shape of the output-polynomial enumeration §3.4 assumes ("enumerate `smallSet m` — output-sized"); that enumeration has to be size-bounded (e.g. by token size with dynamic programming over `rpn` lengths), and FAF's kits have neither. The `SmallList.lean` docstring's "`List.range (4 ^ (K + 1))` is astronomically long" names the wrong culprit (the squaring dominates). Severity: presentation in the handoff; it matters because a continuation would start from the handoff.
