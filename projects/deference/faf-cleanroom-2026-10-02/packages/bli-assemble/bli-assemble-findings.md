# `bli-assemble` — findings about the sources and the dependencies

Per [STANDARDS](../../STANDARDS.md) §5: errors, ill-posed claims, gaps; each with a severity (blocking the note's conclusion / local error / imprecision / presentation) and a pointer. Lean names are in `Cleanroom.Bli.BliAssemble` unless qualified.

## F1 — The expressibility size claim holds for the write-out coding, which `bli-trajectory`'s `StateCoding` abstraction does not force (imprecision, `bli-trajectory` `StateCoding`; `bli-program` §3.4 assumes the write-out coding without a separate clause)

`bli-program` §3.4 says the tent marginal is expressible by "an expression of size polynomial in the atom's own size (its index encodes the `|S_m|` entries of `Q̂`)" — the parenthesis names the write-out coding, implicitly but unambiguously, so the source is right for the coding it has in mind. The gap lives in `bli-trajectory`'s `StateCoding` abstraction: `StateCoding.large` demands only `sizeBound m ≤ log₄ (code m Q)`, and an injective coding may give some grid tables codes of about `sizeBound m` base-4 digits (e.g. `exists_stateCoding`'s `4 ^ sizeBound m + index`, at index `0`), while `tentExpr` has at least one factor per coordinate — at least `|S m|` leaves (`tentExpr_cost_le` is the upper bound; the lower bound is read off the construction, a product over the sorted `S_{m+h+1}`, not proved) — with `|S m|` exponential in `sizeBound m` (`bli-found`'s `sizeBound_lt_card_smallSet` is the weak direction; `|S m|` counts all sentences of token size `≤ 2^{2^m}`). On such an atom the oracle's polynomial output bound `R_length_le` would fail, so L2's hypothesis package is believed inhabitable only at write-out-style codings (ledger, row of record). The coding of record here writes the whole table out (`writeOutCoding`), and the property the claim needs is proved as `writeOutCode_card_le_log : |S m| ≤ log₄ (writeOutCode 𝓜 m Q)`. Pointer: `Coding.lean`; `bli-trajectory` `Defs.lean` (`StateCoding.large`); mandate Context, Known issue 8 (the mandate told the formalizer to file this against §3.4; the source already names the coding, so the pointer was moved here in repair round 1 — round-1 fidelity audit N4, adversarial N9). Severity: imprecision (an API note for `bli-trajectory`: a `StateCoding` field `card_le_log : |S m| ≤ log₄ (code m Q)` would make the claim coding-independent; §3.4 could say "for the written-out state" in its own clause).

## F5 — "The overlay differs from the LIA on every day" holds from `bli-overlay`'s `N₀` on; days `< N₀` are open (imprecision, mandate target 8; corrected in repair round 1)

The mandate's fourth conjunct for target 8 reads: "the state atom is off the LIA's finite day-`n` support, quoted `0` (`liaQuote_eq_zero_of_not_mem_support`), while the tent gives it positive mass". The second half is `bliHistory_pos_on_face`. The first half — that some face point's day-`(n+1)` state atom is off the LIA's day-`n` support — reduces through `bli-superbelief`'s `liaStates_support_subset_firm` to the trading firm's day-`n` strategy support, and that is settled in the run: `bli-overlay`'s gated T2, `firm_support_subset_smallSet` (`N₀ = (C + 16)^2` for the structured-escape constant `C`; `676` at `C = 10`), says every sentence the firm trades on day `n ≥ N₀` is small on day `n`, while a day-`(n+1)` candidate atom is not small on day `n` (`bli-found`'s `stateAtom_large`). Round 0 of this package recorded the firm bound as "FAF-internal and was not derived here", which was true of the package and misleading about the run; the round-1 fidelity audit (B1) composed the three facts in a fourteen-line probe, landed here as `bliHistory_ne_lia_from` (conjunct (8) of `bli_hypotheses_paperDP`): **from `N₀` on, `𝐏` and FAF's LIA over `paperDP 𝗜𝚺₁` differ on some sentence every day**. What remains open is only the first `N₀` days, where the dichotomy `bliHistory_ne_base_on_stateAtoms_dichotomy` (either `𝐏 ≠ liaHistory` on some day-`(n+1)` candidate atom, or the LIA already distributes mass one over the candidates) is all that is proved; closing it would need the LIA's support on days `< N₀`, which `bli-overlay`'s bound does not address. Severity: imprecision in the mandate's expectation ("every day" is "every day from `N₀` on" at the present state of the run); not a source error.

## F6 — The day-varying e.c. reader of mandate target 8 is not delivered; a day-`n` reader of a day-`n` state atom is impossible, a slower-growing one is not ruled out (gap, mandate target 8 "day-varying payload"; corrected in repair round 1)

The mandate asks for "an e.c. trader rewritten non-trivially on every day (adapt `familyReader` to the state family with a day-varying payload)". A trader whose day-`n` coefficient reads `⌜𝑸_{n+1} = q⌝` is not efficiently computable: `MachineSentenceCodes` families are eventually small (`machineSentenceCodes_eventually_small`) and every candidate's state atom is large on its own day (`stateAtom_large`; `not_machineSentenceCodes_nextStateAtoms`). That is the content of `bridge_lemma` and the reason the splice is harmless. It does **not** show that no day-varying e.c. reader exists (round 0 overstated this): a reader of `price ⌜𝑸_{m(n)} = zeroState m(n)⌝ (m(n) − 1)` on day `n`, with `m(n)` growing like `log log log n` (the write-out code has about `|S m|` digits, triply exponential in `m`), names sentences of size polynomial in `n` and is rewritten by the map on every day (`stateAtom_large` at `m(n) − 1 < m(n)`); its `MachineSentenceCodes` certificate needs an enumeration of the candidate codes inside the machine class — the same obstacle as target 6 (iii) — and was not attempted. The reader of record (`stateReader`) names one fixed state atom at day `0`, which the map rewrites on every day (`stateReader_splice_ne`: the splice is not the identity on any day — syntactic, as L1 intends); "day-varying" in the package is the market-side family of face points on which `𝐏` differs from the base. Severity: gap (the trader side of target 8's day-varying ask is not delivered; recorded in the ledger row of `bli_hypotheses_paperDP`).

## F7 — `smallIndex` is defined twice in the dependencies (presentation, `bli-trajectory`/`bli-superbelief`)

`Cleanroom.Bli.BliTrajectory.smallIndex` (`Defs.lean:60`) and `Cleanroom.Bli.BliSuperbelief.smallIndex` (`Paper.lean:48`) are two constants with the same body `⟨smallSet, …⟩`. Severity: presentation (an FAF-style "API request" to the dependencies: one `smallIndex`, in `bli-finite` or `bli-found`).

## F8 — Computability is not free; the shared leaf (`smallList`) is now landed, the two obligations remain open (gap, mandate Known issue 7; updated in repair round 1)

`smallSet` (`bli-found`), `grid`/`chainProbH`/`tentExpr` at `smallIndex` and `writeOutCoding` are all `noncomputable` in Lean's sense. The mathematics is finite; the Lean obstacle is that `smallSet` is a `Finset` of a noncomputable carrier, so every object built on it is noncomputable, and a `Computable`/`FP` proof must re-implement them over a computable enumeration and prove the re-implementation equal. Repair round 1 landed the enumeration (`SmallList.lean`): `smallList n` is a plain compiled `def` with `(smallList n).toFinset = smallSet n`, `Nodup`, sorted by FAF code — by the structural recursion inside `bli-found`'s own finiteness proof, which sidesteps the mandate's converse size bound `encode φ ≤ g (tokenSize φ)` entirely (an API note for `bli-found`: its stretch S1 needs no `g`) — and the alignment `smallSorted_map_val` with `bli-superbelief`'s `encLE` sort, so the write-out digit list is computable from a table's values (`writeOutDigits_eq_smallList`). What the two open statements still need is in `bli-assemble-handoff`: for `bliOv_computableTable`, the grid as a list of numerator vectors, the write-out decoder, the parser and `chainProbH` over lists, and the `Computable` assembly; for `tentOracle_exists`, the `FP` versions of the same, where `smallList` is useless (it is astronomically long) and the oracle must read `|S m|` off the atom's own digits. Severity: gap (known, recorded so that the open rows are not mistaken for oversights).

## F9 — The run-level lookup is definable through FAF's parser, which moves all difficulty into the oracle (presentation, mandate target 6 (i))

The mandate's target 6 (i) asks for a run-level recognizer of Tier-A sentences "under every spelling `parseRpn` accepts". Defining the lookup as `parseRpn`-then-map (`tentExprRun`) makes agreement with the map (`RunAgrees`) hold by construction on every spelling, and is honest: the specification of the oracle (`R_spec`) is literal on the decoded run, and the oracle is free to compute the parse any way it likes. The cost is that the whole difficulty — parsing in `FP`, decoding the write-out code, the tent constants by repeated squaring, the restart constant by the Markov factorization (the naive `chainProbH` sum is exponential; the product of `lastMarg`s is not), the escape-expanded emission and its polynomial bound — sits in one open statement. Recorded so that an auditor does not read `tentRunAgrees` as progress on the hard theorem. Severity: presentation.
