## F1 — (A4)'s two halves separate over FAF; expressibility is true, exploitation is where the work is (severity: local to Theorem 2's proof; would be blocking if T4 failed)

v3 §4 states (A4) as one assumption: "the softened machine is an e.c. trader of the joint class **and** its firing indicator is a joint-generable weighting". Over FAF these are different kinds of statement. The second — (ii), expressibility — is decided **true** here: `adaptFire_pgenerable` (T1) shows the firing feature is a `PGenerableWeighting` for every legal `w`, and `legibleOn_fireSeq_joint` shows joint legibility is closed under the machine. The first — (i), that the machine *trading* on its firing weighting is an e.c. trader whose non-exploitation yields the `H`-side average — is not a consequence of (ii) and is not supplied by v3's "exactly the computation of §3 with `u` in place of `w`": §3's computation runs FAF's Kelly round trip along a *schedule* (the dependency's `hSideBridge`), where consecutive round trips never overlap, and the budget telescopes as a product over closed trips (`feedbackWealth`). The adaptive weighting's pieces overlap (for `f n = 2n+2`, up to `n/2` pieces are open at once; for `2^n`, every `m` with `log₂ n < m < n`, i.e. `n − O(log n)` — the round-0 text said `O(log n)`, which is the count for the *hard* machine, corrected in repair round 1 after audit r1 N10), the Kelly product does not telescope across them, and FAF's own corrected 4.8.16 (`luv_wubexp_ofComputation`) also demands `WeightingSupportedOnDeferralImage`. So "one open position by construction" names a budget argument that §3 does not contain. It is stated as the OPEN `adaptiveBridge` (T4), with the schedule case proved (`adaptiveBridge_of_schedule`), and Theorem 2 ships as `v3Theorem2_of_bridge` with that conclusion as a named hypothesis. Pointer: v3 §4 "(A4)" and the proof of Theorem 2; [fa-adaptive-joint-report](fa-adaptive-joint-report.md) § T4 for the budget design.

## F2 — the product softening over-fires; v3's prose admits both readings, only the additive one is a one-position machine (severity: imprecision in v3 §4; a local error if the product reading is taken)

v3's "composing one bounded-size soft update per day" can be read as the product `flat_n = ∏_{m ∈ window(n)} (1 − fire_m)` (FAF's `armChain` shape, the "natural" softening of a Boolean flat bit) or as the additive `flat_n = 1 − ∑_{m ∈ window(n)} fire_m`. The product reading does **not** keep the total open position at most `1`: `product_softening_overfires` (Lean, Kind N+) exhibits `f n = n + 10`, `r = ½, 1, 1, …`, whose product-law solution has `p = ½, ½, ¼` and open position `5/4` on day `3`; from the half-firing `r_0 = ½` followed by `r ≡ 1`, the running flat value obeys `P_i = P_{i−1}(1 − P_{i−1})` from `P_1 = ½` and decays like `1/i`, so the open total diverges logarithmically (not formalized; from a flat start with `r ≡ 1` outright the product law gives `p = 1, 0, 0, …` — the round-0 text omitted the initial half-firing, audit r1 adversarial N6). The additive reading keeps `open ∈ [0, 1]` on every day for every solution (`FireRec.nonneg_openMass_le_one`, Kind P) and is the sum form of the update v3 names, `open (n+1) = open n + fire n − (pieces closing at n+1)` (`openMass_succ`). The package uses the additive form throughout. Pointer: v3 §4 "(A4)", the sentence quoted; mandate trap (α).

## F3 — "size linear in `n`" is not the FAF notion; polynomial-time emission is. For v3's own `2^n` the size claim is right as a tree; `letE` sharing is used here for a general lookahead, not forced (severity: presentation; settled; corrected in repair round 1)

v3 says the firing indicator is "an expression of size linear in `n`, built from products, maxima and ramps". Over FAF the admissible notion is `PGenerableWeighting`: the serialization is a `MachineSpliceStream` (emitted in polynomial time on the unary day), rank `≤ n`, closed. Two remarks on the sentence. (a) **Tree size depends on the encoding and the lookahead** (the round-0 text claimed "without sharing the firing expression is not polynomial", which is false for v3's own `2^n`; audit r1 B3). In the *open-sum* encoding (`openExpr`: `open n = ∑_{m<n, n<f m} fire m`, each `fire m` a subtree) the day-`n` tree satisfies `S(n) ≥ ∑_{m ∈ window(n)} S(m)`, exponential for `f n = 2n+2` (`≥ S(n−1) + S(n−2)`) and for `f n = 2^n` alike (the open pieces are all `m` with `log₂ n < m < n`). In the *state-passing* encoding v3 actually describes ("composing one bounded-size soft update per day"), `open (n+1) = open n · (1 − r n) + r n − [n+1 ∈ im f] · fire m` with `m` the piece closing at `n+1` (the values coincide with the open-sum form by `openMass_succ`), `open n` is mentioned once and `fire m` only on closing days: for `f n = 2^n`, closings happen only at powers of two with `m = log₂(n+1)`, so `T(n) ≤ ∑_{k<n} (|r_k| + c) + ∑_{j ≤ log₂ n} (T(j) + |r_j|) = O(n · max_k |r_k|)` — a tree in the paper's literal grammar (`+`, `×`, `max`, constants, price features), rank `≤ n`, essentially *linear in `n`* times the size of one ramp, exactly v3's claim; for a linear lookahead `f n = 2n+2`, by contrast, `T(n+1) = T(n) + T(⌈n/2⌉) + O(1)`, i.e. `n^{Θ(log n)}`, superpolynomial. So (A4)'s size claim is **right for v3's parameters**, and the package's `letE` straight-line program (`chainList`: serialization length `O(n²)` plus `O(n)` copies of `w`'s, `serialize_adaptFire`; licensed by the LI paper's footnote tex:788 as FAF's `EF` docstring records) is what makes the *general-lookahead* theorem T1 go through — sharing is used, not forced. An `adaptFireTree` for `f n = 2^n` in the sharing-free grammar, with its size bound, is a natural stretch not built here (hand computation; the mandate's § T1 already gave the recursion). (b) The membership `n < f m` of the open sum is decided at emission time from `f.graph_fp` (`openCount_ruler`), which is where "e.c." lives; root-fa-020's flag that v3 never checks the composition's cost is answered by `adaptFire_spliceStream`. Pointer: v3 §4 "(A4)"; root-fa-020; mandate § T1 (the sharing-free recursion).

## F4 — Corollary 3 understates what Corollary 2 gives: finite support, not just a finite sum (severity: presentation)

v3 §5 Corollary 3 states `∑_n w_n < ∞` for every rational triple. Corollary 2 (`Dominates`: `∀ c > 0, ∀ᶠ n, a_n − c < h_n`) at `c = ε` gives `a_n − ε < h_n` eventually, which makes the lower ramp `Ind_δ(h_n < t − ε)` vanish wherever the upper one is positive — every rational-parameter violation weight is **eventually zero**, `v3Corollary3_eventually_zero_of_bridge` (and the summability form `v3Corollary3_summable_of_bridge` follows). v3's own *proof* of Corollary 3 already says "there are finitely many such days"; the understatement is in the *statement* (`∑ w_n < ∞`) only, so this is presentation, not a missed fact (audit r1 adversarial N7). Pointer: v3 §5 Corollaries 2–3; li-asymp-calc `Dominates.viol_eventually_zero`.

## F10 — v3's "at most one position is ever open" is true of the hard machine and false of the soft one, which is the point of `OnePosition` (severity: imprecision)

v3 §3 and vq-wiki-057 speak of "one position at a time"; the softened machine (A4) holds *fractional* positions on several pieces at once — for `f n = 2n+2` up to `n/2` pieces, and `onePosition_positive_everywhere` has a piece open on *every* day.
